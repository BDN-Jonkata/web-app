## Структура на проекта

`web-app` е името на GitHub repository-то и папката на клонираното repository.
Няма втори вложен `web-app/`: `frontend/`, `backend/`, `shared/` и общият
`package.json` са директно в корена. Същата структура се използва във всички
работни branches. При клониране на repository-то изпълнявай общите npm команди
от този корен, а не от несъществуваща вътрешна папка.

```text
web-app/
├── frontend/           React 19, Vite 6 и всички UI файлове
│   ├── src/            компоненти, стилове, диктовка, история, симулация и frontend тестове
│   ├── public/         интерактивна карта, изображения и шрифтове
│   └── scripts/        генериране и оптимизиране на географската карта
├── backend/            Node.js / Express 5 API
│   ├── src/            маршрути, профили, база данни, AI адаптери, DAOs, DTOs и тестове
│   │   ├── ai/         Groq интеграция, контекст и грешки
│   │   ├── DAOs/       Data Access Objects за базата (User, Session, Conversation, Message)
│   │   ├── DTOs/       Data Transfer Objects и саниране на данни
│   │   ├── openapi/    OpenAPI 3.1.0 спецификация и маршрути
│   │   └── testing/    in-memory хранилища за бързи тестове
│   ├── prisma/         PostgreSQL схема и миграции
│   ├── scripts/        Prisma CLI с правилно зареждане на конфигурацията
│   ├── server/         отделен минимален health demo сървър
│   ├── .env.example    примерна backend конфигурация с пълни описания
│   └── .env            лична конфигурация — не влиза в git
└── shared/             общ енергиен модел, API договори и валидация
    ├── energy.js       изчисления на енергийния микс, часови профили и централи
    ├── chatContract.js валидация на чат съобщения и позволени UI корекции
    └── simulationContract.js валидация и нормализиране на симулационни таймлайни
```

`shared` се използва от frontend и backend, за да няма две различни версии
на симулацията и входната валидация. Коренът съдържа само общите npm команди,
lockfile, `.gitignore` и тази документация. Микрофонът е frontend функция;
Groq ключът, SMTP паролите и достъпът до PostgreSQL остават само в backend-а.

Главният API се стартира от `backend/src/index.js` на порт 3001. Запазен е и
отделният минимален health demo на съотборника в `backend/server/server.js`;
той не заменя API-то за вход, история, симулации и AI. По желание го стартирай с
`npm run dev:demo --prefix backend` (порт 3000 по подразбиране).
Prisma Studio се отваря с `npm run db:studio`, използвайки backend конфигурацията.

## Бързо стартиране

Изпълни от корена на repository-то (`web-app`) с Node.js 22 или по-нова версия:

Ако `backend/.env` липсва, копирай `backend/.env.example` в `backend/.env`
и настрой стойностите. Не презаписвай съществуващия файл с настройки.

```sh
npm install
npm install --prefix frontend
npm install --prefix backend
npm run db:generate
npm run dev
```

- **Frontend**: http://localhost:5173
- **API**: http://127.0.0.1:3001
- **Интерактивна API документация (Scalar)**: http://127.0.0.1:3001/reference
- **OpenAPI спецификация**: http://127.0.0.1:3001/openapi.json

Vite препраща `/api` към backend-а. Express зарежда точно
`web-app/backend/.env`, независимо от текущата работна папка.
За стари локални копия се използва `web-app/.env` само ако
`backend/.env` липсва. Prisma командите използват същото правило.

Самостоятелно стартиране от `web-app`:
- `npm run dev:frontend` — само React / Vite frontend
- `npm run dev:backend` — само Express backend с `--watch`
- `npm run dev` — паралелно стартиране на frontend и backend чрез `concurrently`

## Гласова диктовка

Бутонът с микрофон до изпращането използва Web Speech API на браузъра,
без допълнителен API ключ и без промени по backend-а. Натисни го, разреши
микрофона и говори; текстът се появява в полето в реално време. Натисни „Спри диктовката“
(или Escape/Enter в полето), изчакай завършването и прегледай/редактирай текста.
Съобщението се изпраща само с отделно натискане на изпращане или Enter.
Диктовката добавя към съществуващия текст, а не го изтрива.

Езикът е `bg-BG` или `en-GB`, според настройката на интерфейса. Полето е
временно само за четене, докато тече разпознаване, за да не се презаписват
ръчни редакции. Отваряне на менюто, свиване на чата, промяна на езика или
смяна на разговор спират микрофона; вече показаният текст остава в черновата,
освен при изрично отваряне/създаване на друг разговор.

Поддръжката зависи от браузъра и услугата му за разпознаване, включително
наличните езици. Опитай Chrome на HTTPS или localhost с интернет връзка.
При липса на поддръжка или отказано разрешение се показва обяснение;
ръчното писане остава достъпно. Приложението не записва аудио в своя backend,
но браузърът може да го изпраща към външна услуга за разпознаване.
Не използвай диктовката за тайни или чувствителна информация.
Документация: https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition.

## Настройки, профили и история

Един бутон за меню в заглавната лента на чата отваря страничен панел (drawer),
който се плъзга отдясно наляво върху чатбота. Картата, статистиките и чатът
не променят размерите си. Панелът съдържа история, настройки и профил:

- Вход, регистрация с имейл/парола и изход.
- Бял, тъмен и системен режим, плюс бонус теми „Горски“ (`forest`) и „Залез“ (`sunset`).
  Системният режим следва настройката на устройството, включително при промяна.
- Български или английски език за интерфейса и новите AI отговори.
  Старите съобщения остават на езика, на който са написани.

Настройките се запазват в браузъра; за влезли потребители — и в PostgreSQL.
Разделът „История“ в панела позволява отваряне на разговор или започване на
нов. Панелът се затваря с Escape, бутона за затваряне или клик извън него.
Отварянето на разговор възстановява съобщенията и сценария на картата,
като спира автоматичната симулация. Показват се последните 50 разговора и се
запазват до 80 съобщения на разговор.

Гостите могат да използват приложението без база данни. Тяхната история е
само в `localStorage` на текущия браузър — видима е за други хора, използващи
същия браузърен профил. Историята на профилите е отделна, проверява се по
потребител и не се записва в `localStorage`. Гост историята не се прехвърля
автоматично в профил при вход. Грешка при запазване се показва в интерфейса.

### PostgreSQL за вход и история между устройства

Стартирай PostgreSQL, създай база и настрой `DATABASE_URL` в `web-app/backend/.env`.
Примерът в `.env.example` използва база `jev_router`; промени адреса,
потребителя и паролата според локалната си инсталация. После, от корена `web-app`:

```sh
npm run db:generate
npm run db:migrate
npm run dev
```

`db:migrate` прилага включените Prisma миграции, без reset на базата.
Ако вече имаш стара база, създадена с `db:push`, първо направи backup и сравни
схемата ѝ с началната миграция. Само ако съвпада със схемата преди добавянето на
профилите, отбележи началната миграция като приложена:

```sh
cd backend
node scripts/prisma.mjs migrate resolve --applied 20261002000000_initial
cd ..
npm run db:migrate
```

При различна съществуваща схема е необходимо отделно baseline/съгласуване,
а не изтриване на таблици. Не използвай reset върху база с нужни данни.

Паролите се хешират със salted scrypt. Сесиите са със случайни токени в
HttpOnly/SameSite cookies; в базата се пази само хешът на токена. Сесията е
валидна седем дни и изходът я анулира. За production са необходими HTTPS и
`NODE_ENV=production`, за да бъдат cookies и `Secure`.

Входът и регистрацията изискват шестцифрен код по имейл. Паролата сама по себе
си не създава сесия. Кодът е за текущия браузър, валиден е 10 минути, с до 5
опита. Повторното изпращане има 60 секунди пауза и не удължава срока или
нулира опитите. Допускат се до 5 нови заявки на час за профил и до 3 изпращания
за един код. Отделно има лимити по IP.

### Имейли, 2FA верификация и забравена парола

В `backend/.env` добави настройките от своя SMTP доставчик:

```dotenv
SMTP_HOST=smtp.your-provider.example
SMTP_PORT=587
SMTP_USER=your-smtp-user
SMTP_PASS=your-smtp-password
EMAIL_FROM="Energy Bulgaria <noreply@your-domain.example>"
```

Използвай реалните настройки на доставчика, не примерните стойности. При
порт 465 се използва TLS от началото; при 587 се изисква STARTTLS. Няма
автоматичен фалшив имейл/Ethereal, fallback парола или записване на кодове и
пароли в логовете. [SMTP настройки в Nodemailer](https://nodemailer.com/smtp).
За локален mail catcher на `localhost` може да зададеш `SMTP_PORT=1025` и
`SMTP_ALLOW_INSECURE=true`; това не се допуска в production или за външен host.

От корена на repository-то (`web-app`):

```sh
npm run db:migrate
npm run db:generate
npm run dev:backend
```

Миграцията `20261004000000_email_auth` добавя таблиците `AuthChallenge` и
`EmailNotification`. Тя прекратява **съществуващите сесии веднъж**, за да не
заобикалят потвърждаването; не изтрива профили или разговори и не seed-ва данни.
Старите непотвърдени профили потвърждават имейла при следващ вход.

„Забравена парола?“ в прозореца за вход изпраща отделен код за възстановяване.
След код + нова парола, въведена два пъти, всички сесии и неизползвани кодове
на профила се анулират. Нужно е нормално влизане с новата парола и нов имейл код.
Само сесия/Bearer токен или стар HMAC линк вече не могат да сменят паролата.
При искане на възстановяване и повторно изпращане отговорът не разкрива дали
профилът съществува; липсващите профили не получават имейл. Принципи за
възстановяване: [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

След смяна се изпраща известие с време (UTC), IP адрес и браузър/устройство.
Ако SMTP не работи, паролата остава сменена, а известието се пази в PostgreSQL
и backend-ът опитва повторно всяка минута с backoff. Изпратените известия и
старите кодове се почистват след седем дни. При прекъсване след изпращане е
възможно повторно известие (at-least-once delivery).

Приблизително местоположение може да се добави с `IPINFO_TOKEN`.
`IPINFO_PLAN=lite` връща държава; `lookup` изисква подходящ план за град/регион.
Това е opt-in: IP адресът се изпраща до IPinfo. Без настройка или при грешка
известието честно показва „Недостъпно“; за локални IP адреси — „Локална/частна
мрежа“. Частни IP адреси не се изпращат за геолокация. Местоположението може
да е това на VPN, а не реалното място. [IPinfo документация](https://ipinfo.io/developers).
При reverse proxy настрой `TRUST_PROXY` само с точните адреси/CIDR на proxy-то;
никога с `true` или произволен брой hops. Иначе се използва socket IP, а
подаден от клиента `X-Forwarded-For` се игнорира.

API: `POST /api/auth/register`, `/login`, `/verify-code`, `/resend-code`,
`/forgot-password`, `/reset-password`. Първите два и forgot-password връщат
202 и само краткосрочна HttpOnly verification cookie; verify-code връща
сесията. Мутациите изискват CSRF header. Документация: `/reference`.

### Модел на потребителите и DAOs / DTOs

Селективно са пренесени и интегрирани разширените полета на профилите:
username, реално име, телефон, аватар, биография, роли `USER`/`ADMIN`/`MODERATOR`,
статус на профила, флаг за потвърден имейл (`isEmailVerified`), `updatedAt`,
връзки към проекти/съобщения и индекси.

Архитектурата на базата данни е структурирана в слоеве:
- **DAOs** (`backend/src/DAOs/`): капсулират директния достъп до базата през Prisma Client
  (`userDao`, `sessionDao`, `conversationDao`, `messageDao`, `projectDao`, `projectSkeletonDao`, `modelRouteDao`, `relationsDao`).
- **DTOs** (`backend/src/DTOs/`): филтрират и санират данните, скривайки паролни хешове,
  вътрешни токени и служебни метаданни преди предаване към клиента.

Регистрацията не позволява клиентът да задава роля или статус. Неактивните
профили не могат да влизат или да използват стара сесия. Съобщенията на
потребител получават автора си от сесията; AI съобщенията нямат потребител-автор.
Не е добавено отделното поле `password`: пази се единствено `passwordHash`.

Миграцията `20261003101500_user_profiles` попълва `updatedAt` за
съществуващите профили от `createdAt`, преди колоната да стане задължителна.
При база с предходни миграции направи backup, изпълни `npm run db:migrate`,
после `npm run db:generate` и рестартирай backend-а. Миграциите не се прилагат
автоматично при стартиране на приложението.

Ако базата вече е мигрирана с външна миграция `20261003093750_1st`, не прилагай
сляпо тази миграция: колоните/enum-ът вече съществуват, а схемите и историята
трябва да се съгласуват отделно след backup. Не използвай reset или произволно
`migrate resolve`. Старите миграции тук са оставени непроменени.

Redis не е необходим за този еднопроцесен backend: PostgreSQL съхранява
профилите, сесиите и разговорите, а rate limiting е в паметта на процеса.
При няколко backend инстанции може да се добави Redis за споделени лимити.

## Временен AI — Groq

1. Създай акаунт и API ключ на https://console.groq.com/keys.
2. Използвай **Free plan** за тестване. Той има квоти и не е неограничен:
   https://console.groq.com/docs/rate-limits.
3. Добави следните настройки в `web-app/backend/.env`:

```dotenv
AI_PROVIDER=groq
GROQ_API_KEY=your_actual_key_here
GROQ_MODEL=qwen/qwen3.8-27b
CHAT_DAILY_BUDGET=2000
```

4. Рестартирай `npm run dev` след промяна на ключа.

Ключът се използва само от Express. Никога не го добавяй в React, с префикс
`VITE_`, в git или в чат. `.env` е изключен чрез `.gitignore`.
API ключът е необходим — приложението не включва споделен публичен ключ.
Няма автоматично преминаване към платен модел или друг доставчик.
Без ключ чатът показва конкретна грешка, а не измислен „AI“ отговор.

Моделът отговаря на избрания език и получава скорошната история и текущия сценарий.
Express изчислява контекста със същата симулация, която използва интерфейсът.
При изрична команда може да променя сезон, час, облачност, вятър, слоеве и
избран град/централа. Всички предложени промени са ограничени до тези контроли.

Съобщенията, историята и сценарият се изпращат на Groq. Не изпращайте лични
данни или тайни при тестване. Историята се запазва според режима гост/профил,
описан по-горе. PostgreSQL не е необходим за самата AI интеграция.

Groq моделите и квотите могат да се променят. Моделът е конфигурируем чрез
`GROQ_MODEL`; проверете https://console.groq.com/docs/models.
Адаптерът очаква модел с JSON Object Mode. По подразбиране Qwen 3.8 работи
без допълнително reasoning за по-кратки тестови заявки.

Защита на квотата: освен локален лимит от 10 заявки/минута/IP и 60 заявки/час/IP,
е дефиниран и общ дневен лимит за всички клиенти чрез `CHAT_DAILY_BUDGET` (по подразбиране 2000 заявки за 24 часа).

## AI симулация, решения и SSE потоци в реално време

В допълнение към чат асистента, backend-ът съдържа специализирана подсистема
за приемане, валидиране и визуализиране на енергийни решения и таймлайни,
генерирани от външни AI агенти или автоматизирани оптимизатори:

### Приемане на симулационно решение (`POST /api/simulation/decision`)

Позволява на AI агент или външен скрипт да изпрати готово симулационно решение,
съдържащо обобщение, диспечерски действия, сценарий и състояния на компонентите:

```json
{
  "prompt": "Зимна буря в 19:00 часа с включване на ПАВЕЦ Белмекен на пълна мощност",
  "decision": {
    "answer": "ПАВЕЦ Белмекен е пусната на 100% капацитет за покриване на пика.",
    "summary": "Пиковото потребление е балансирано чрез хидроенергия и АЕЦ Козлодуй.",
    "actions": [
      {
        "component": "hydro",
        "action": "dispatch_max",
```

- Входните данни се проверяват стриктно от `shared/simulationContract.js`.
- Непълни обекти или невалидни числови стойности се санират без да чупят визуализацията.
- Поддържат се единични състояния или мулти-стъпкови времеви поредици (`frames`) за анимация на диспечерски графици.

#### Компактен формат (`"v": 2`) — препоръчителен за AI агенти

Същите данни с около 4 пъти по-малко байтове. Backend-ът ги разгръща до
пълния формат по-горе, така че визуализацията е идентична:

```json
{
  "v": 2,
  "prompt": "Зимна буря в 19:00 с ПАВЕЦ Белмекен на пълна мощност",
  "answer": "ПАВЕЦ Белмекен е пусната на 100% за покриване на пика.",
  "actions": [["hydro", "dispatch_max", "belovo", 736]],
  "scenario": { "season": "winter", "cloud": 95, "wind": 25, "stepMs": 1200 },
  "frames": [
    {
      "hour": 19, "label": "19:00 Пик", "demand": 4276,
      "mw": { "solar": 0, "wind": 76, "hydro": 1339, "other": 35 },
      "sectors": { "Индустрия": 1700, "Домакинства": 1300, "Услуги и търговия": 900, "Транспорт и селско ст.": 376 },
      "sites": { "belovo": 736, "krichim": 261 },
      "cities": { "sofia": [1450, 800], "plovdiv": [620, 400] },
      "flows": [["belovo", "sofia"], ["belovo", "plovdiv"]],
      "nuclear": 2000,
      "notes": { "belovo": "Пусната на 100%" }
    },
    { "mw": { "hydro": 1200 }, "sites": { "belovo": 600 }, "cities": { "sofia": [1450, 700] } }
  ]
}
```

| Поле | Тип | Значение |
|---|---|---|
| `v` | `2` | Включва компактния формат. Без него се очаква пълният формат. |
| `prompt` | `string` | Задължително. Сценарият, показан над картата. |
| `answer` | `string` | Решението на агента. |
| `actions` | `[component, action, target, value][]` | Диспечерски действия; `value` е в MW и не е задължително. |
| `scenario` | `{season, cloud, wind, stepMs}` | `season`: `winter`/`spring`/`summer`/`autumn`; `cloud`, `wind`: 0–100; `stepMs`: 200–10000 ms на кадър. |
| `frames[].hour` | `number` | 0–24. Ако липсва: предишният кадър + 1 (първият: `scenario.hour` или 12). |
| `frames[].label` | `string` | Не е задължително; по подразбиране `HH:MM` от `hour`. |
| `frames[].demand` | `number` | Потребление в MW. Без него кадърът няма статистика. |
| `frames[].mw` | `{solar, wind, hydro, other}` | Производство от ВЕИ в MW. Сумата им е `res`; покритие и баланс се изчисляват. |
| `frames[].res` | `number` | Само ако няма `mw`: общо производство от ВЕИ. |
| `frames[].sectors` | `{име: MW}` | Дяловете и цветовете се изчисляват. |
| `frames[].sites` | `{siteId: MW}` | Текуща мощност на централа. |
| `frames[].cities` | `{cityId: [потребление MW, получено от ВЕИ MW]}` | |
| `frames[].flows` | `[from, to, mw?][]` | Линии централа → град на картата. |
| `frames[].nuclear` | `number` | Мощност на АЕЦ Козлодуй в MW. |
| `frames[].notes` | `{id: string}` | Бележка на агента за град, централа или `kozloduy`. |

Всеки следващ кадър наследява полетата, които не съдържа. `mw`, `sectors`,
`sites`, `cities` и `notes` се сливат по ключ, така че в таймлайн се праща
само това, което се променя. `label` не се наследява.

### Поточни събития в реално време (`GET /api/simulation/events`)

Frontend клиентите се абонират за Server-Sent Events (SSE) на този адрес.
Всяка промяна чрез `/api/simulation/decision` или `/api/simulation/reset`
незабавно изпраща събитие (`init`, `update`, `reset`) към всички отворени браузъри,
сървърът поддържа heartbeat на всеки 15 секунди и ограничава броя едновременни потоци до 100.

### Защита с API ключ (`SIMULATION_API_KEY`)

- За локална разработка: ако `SIMULATION_API_KEY` не е зададен в `.env`, записващите операции са свободни.
- За production: настройването на `SIMULATION_API_KEY` е задължително. Всички заявки към
  `POST /api/simulation/decision` и `POST /api/simulation/reset` изискват заглавка:
  `X-Api-Key: <your_secret_simulation_key>`. Без нея сървърът връща `401 Unauthorized`.

### Конзолни помощници за тестване във frontend

В режим на разработка (`npm run dev`), във frontend браузърната конзола са достъпни глобални помощници:
- `window.setSimulationData(payload)` — изпраща решение директно от Developer Tools.
- `window.resetSimulation()` — изчиства активната симулация.

## Интерактивна API документация — Scalar & OpenAPI

Проектът разполага с пълна **OpenAPI 3.1.0** спецификация и модерен интерактивен интерфейс,
базиран на **Scalar** (`@scalar/express-api-reference`), за бързо тестване и интеграция на всички endpoints:

- **Scalar UI**: http://127.0.0.1:3001/reference (също http://127.0.0.1:3001/docs и `/scalar`)
- **OpenAPI JSON**: http://127.0.0.1:3001/openapi.json

### Възможности на Scalar интерфейса:
1. **Интерактивно тестване**: директно изпращане на тестови заявки през браузъра без нужда от Postman или cURL.
2. **Автентикация**:
   - `bearerAuth`: въвеждане на Bearer сесиен токен за защитени endpoints.
   - `cookieAuth`: автоматично използване на `energy_session` бисквитки.
   - `verificationCookie`: тестване на стъпковата 2FA верификация (`energy_verification`).
3. **Автоматичен CSRF байпас**: заявки, изпратени от `/reference`, се разпознават автоматично от CSRF защитата.
4. **Контрол за Production**: в production документацията е изключена по подразбиране (връща 404),
   освен ако не е изрично активирана с `ENABLE_API_DOCS=true` в `.env`.

## Списък на API маршрутите

### Автентикация и профил (`/api/auth`)

| Метод | Път | Заглавки / Auth | Описание |
|---|---|---|---|
| `POST` | `/api/auth/register` | CSRF header | Започва регистрация, изпраща 6-цифрен код по имейл, задава verification cookie. |
| `POST` | `/api/auth/login` | CSRF header | Проверява парола, изпраща 6-цифрен код по имейл, задава verification cookie. |
| `POST` | `/api/auth/verify-code` | CSRF header + Cookie | Потвърждава имейл кода и издава активна сесия (HttpOnly cookie + token). |
| `POST` | `/api/auth/resend-code` | CSRF header + Cookie | Изпраща нов код след изтичане на 60 сек. кулдаун (до 3 опита за challenge). |
| `POST` | `/api/auth/forgot-password` | CSRF header | Заявява код за възстановяване на парола (не разкрива дали профилът съществува). |
| `POST` | `/api/auth/reset-password` | CSRF header + Cookie | Сменя паролата, анулира всички стари сесии и нарежда имейл предупреждение за сигурност. |
| `GET` | `/api/auth/session` | Сесийна бисквитка | Връща текущия влязъл потребител или `null`. |
| `POST` | `/api/auth/refresh-token` | CSRF header + Cookie | Подновява активна сесия. |
| `POST` | `/api/auth/logout` | CSRF header + Cookie | Анулира сесията в базата и изчиства сесийната бисквитка. |
| `PUT` | `/api/auth/preferences` | CSRF header + Auth | Обновява темата (`light`, `dark`, `forest`, `sunset`, `system`) и езика (`bg`, `en`). |

### История на разговорите (`/api/conversations`)

| Метод | Път | Заглавки / Auth | Описание |
|---|---|---|---|
| `GET` | `/api/conversations` | Auth изискван | Списък с последните разговори на потребителя. |
| `GET` | `/api/conversations/:id` | Auth изискван | Зарежда пълен разговор със съобщения и запазен сценарий на картата. |
| `PUT` | `/api/conversations/:id` | CSRF header + Auth | Запазва или обновява разговор и симулационно състояние. |

## Бъдещ MCP адаптер

Когато AI екипът е готов:

1. Добавете `backend/src/ai/mcp.js` с избрания MCP клиент, транспорт,
   автентикация и действителното име/схема на инструмента.
2. Адаптерът предоставя `status()` и
   `generate({message,history,state,language}, {signal})`.
3. Нормализирайте резултата до `{reply,patch,provider,model}` и го
   регистрирайте в `backend/src/ai/provider.js`.
4. Задайте `AI_PROVIDER=mcp` в `backend/.env`. Frontend и API договорът остават
   същите; валидирането на контролите остава в Express.

> [!IMPORTANT]
> **MCP още не е реализиран или свързан.** Днес `AI_PROVIDER=mcp` връща ясна
> грешка, вместо да симулира връзка. Необходимите endpoint, транспорт и tool
> schema трябва да бъдат предоставени от външния MCP сървър.

## Тестове и проверки

Проектът разполага с цялостна тестова система без външни платени зависимости:

```sh
npm test
npm run build
```

При изпълнение на `npm test` от корена автоматично се тестват:
1. **Общи договори и архитектура** (`shared/`):
   - `shared/structure.test.js`: архитектурна цялост, имена на папки, липса на остатъчни legacy структури, правилен import graph.
   - `shared/simulationContract.test.js`: нормализиране на симулационни таймлайни, саниране на МВт мощности, географски обекти и цветове.
2. **Backend тестове** (`backend/`):
   - `ai.test.js`: тестване на контекста и грешките с mock HTTP отговори (без харчене на Groq квота).
   - `accounts.test.js`: salted scrypt хеширане, сесии, изолация между потребители и CSRF защита.
   - `emailAuth.test.js` и `emailAuth.http.test.js`: 6-цифрени кодове, опити за налучкване, кулдаун, възстановяване на парола и лимити.
   - `DAOs/daos.test.js` и `DTOs/dtos.test.js`: целокупност на базисните обекти, сериализация и скриване на конфиденциални данни.
   - `simulationRoutes.test.js`: поглъщане на симулации, таймлайни, защита с API ключ и SSE излъчване.
   - `server/server.test.js`: проверка на резервния demo health сървър и Scalar интеграцията.
3. **Frontend тестове** (`frontend/`):
   - `mapLabels.test.js`: четимост и разположение на етикетите върху картата при различни резолюции.
   - `settings.test.js`: теми, езици, запазване на гост история и лимит до 50 разговора.
   - `drawer.test.js`: достъпност (a11y), фокус при Tab/Escape, анимация и затваряне при клик извън панела.
   - `speechRecognition.test.js`: Web Speech API, чернови, липса на презаписване и сигурност.
   - `panelSizing.test.js`: респонсивен дизайн, минимални ширини и разделител между картата и чата.
   - `simulationVisualization.test.js`: правилно визуализиране на кадри и таймлайни без фалшиви данни.
   - `authFlow.test.js`: диалогови прозорци за вход, верификационни таймери и двуезичен интерфейс.

Live проверка на AI чата: добави своя Groq ключ в `backend/.env` и изпрати съобщение през браузъра на http://localhost:5173.
API по подразбиране слуша само на 127.0.0.1. Не го публикувайте публично без production защити и лимити.
