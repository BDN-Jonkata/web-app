# Енергия България

React интерфейс и Express backend за образователна симулация на българската
енергийна система. Часовите профили, секторните дялове и регионалните потоци са
моделни оценки, а не данни в реално време.

## Структура на проекта

```text
web-app/
├── frontend/           React, Vite и всички UI файлове
│   ├── src/            компоненти, стилове, диктовка, история и frontend тестове
│   ├── public/         карта, изображения и шрифтове
│   └── scripts/        генериране на географската карта
├── backend/            Node.js / Express API
│   ├── src/            маршрути, профили, база данни, AI адаптери и backend тестове
│   ├── prisma/         PostgreSQL схема и миграции
│   ├── scripts/        Prisma CLI с правилното зареждане на конфигурацията
│   ├── .env.example    примерна backend конфигурация
│   └── .env            лична конфигурация — не влиза в git
└── shared/             общ модел, API договори и проверки на структурата
```

`shared` се използва от frontend и backend, за да няма две различни версии
на симулацията и входната валидация. Коренът съдържа само общите npm команди,
lockfile, `.gitignore` и тази документация. Микрофонът е frontend функция;
Groq ключът и достъпът до PostgreSQL остават само в backend-а.

## Стартиране

Изпълни от папката `web-app` с Node.js 22 или по-нова версия:

Ако `backend/.env` липсва, копирай `backend/.env.example` в `backend/.env`
и настрой стойностите. Не презаписвай съществуващия файл с настройки.

```sh
npm install
npm install --prefix frontend
npm install --prefix backend
npm run db:generate
npm run dev
```

Frontend: http://localhost:5173. API: http://127.0.0.1:3001.
Vite препраща `/api` към backend-а. Express зарежда точно
`web-app/backend/.env`, независимо от текущата работна папка.
За стари локални копия се използва `web-app/.env` само ако
`backend/.env` липсва. Prisma командите използват същото правило.

Самостоятелно стартиране от `web-app`: `npm run dev:frontend` или
`npm run dev:backend`. `npm run dev` стартира и двете.

## Гласова диктовка

Бутонът с микрофон до изпращането използва Web Speech API на браузъра,
без допълнителен API ключ и без промени по backend-а. Натисни го, разреши
микрофона и говори; текстът се появява в полето. Натисни „Спри диктовката“
(или Escape/Enter в полето), изчакай завършването и прегледай/редактирай текста.
Съобщението се изпраща само с отделно натискане на изпращане или Enter.
Диктовката добавя към съществуващия текст, а не го изтрива.

Езикът е `bg-BG` или `en-GB`, според настройката на интерфейса. Полето е
временно само за четене, докато тече разпознаване, за да не се презаписват
ръчни редакции. Отваряне на менюто, свиване на чата, промяна на езика или
смяна на разговор спират микрофона; вече показаният текст остава в черновата,
освен при изрично отваряне/създаване на друг разговор.

Поддръжката зависи от браузъра и услугата му за разпознаване, включително
наличните езици. Опитай Chrome на HTTPS или localhost с интернет връзка.
При липса на поддръжка или отказано разрешение се показва обяснение;
ръчното писане остава достъпно. Приложението не записва аудио в своя backend,
но браузърът може да го изпраща към външна услуга за разпознаване.
Не използвай диктовката за тайни или чувствителна информация.
Документация: https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition.

## Настройки, профили и история

Един бутон за меню в заглавната лента на чата отваря страничен панел,
който се плъзга отдясно наляво върху чатбота. Картата, статистиките и чатът
не променят размерите си. Панелът съдържа история, настройки и профил:

- Вход, регистрация с имейл/парола и изход.
- Бял, тъмен и системен режим, плюс бонус теми „Горски“ и „Залез“.
  Системният режим следва настройката на устройството, включително при промяна.
- Български или английски език за интерфейса и новите AI отговори.
  Старите съобщения остават на езика, на който са написани.

Настройките се запазват в браузъра; за влезли потребители — и в PostgreSQL.
Разделът „История“ в панела позволява отваряне на разговор или започване на
нов. Панелът се затваря с Escape, бутона за затваряне или клик извън него.
Отварянето на разговор възстановява съобщенията и сценария на картата,
като спира автоматичната симулация. Показват се последните 50 разговора и се
запазват до 80 съобщения на разговор.

Гостите могат да използват приложението без база данни. Тяхната история е
само в `localStorage` на текущия браузър — видима е за други хора, използващи
същия браузърен профил. Историята на профилите е отделна, проверява се по
потребител и не се записва в `localStorage`. Гост историята не се прехвърля
автоматично в профил при вход. Грешка при запазване се показва в интерфейса.

### PostgreSQL за вход и история между устройства

Стартирай PostgreSQL, създай база и настрой `DATABASE_URL` в `web-app/backend/.env`.
Примерът в `.env.example` използва база `jev_router`; промени адреса,
потребителя и паролата според локалната си инсталация. После, от `web-app`:

```sh
npm run db:generate
npm run db:migrate
npm run dev
```

`db:migrate` прилага включените Prisma миграции, без reset на базата.
Ако вече имаш стара база, създадена с `db:push`, първо направи backup и сравни
схемата ѝ с началната миграция. Само ако съвпада със схемата преди добавянето на
профилите, отбележи началната миграция като приложена:

```sh
cd backend
node scripts/prisma.mjs migrate resolve --applied 20261002000000_initial
cd ..
npm run db:migrate
```

При различна съществуваща схема е необходимо отделно baseline/съгласуване,
а не изтриване на таблици. Не използвай reset върху база с нужни данни.

Паролите се хешират със salted scrypt. Сесиите са със случайни токени в
HttpOnly/SameSite cookies; в базата се пази само хешът на токена. Сесията е
валидна седем дни и изходът я анулира. За production са необходими HTTPS и
`NODE_ENV=production`, за да бъдат cookies и `Secure`.
Няма възстановяване на парола или потвърждаване на имейл в тази тестова версия.

Redis не е необходим за този еднопроцесен backend: PostgreSQL съхранява
профилите, сесиите и разговорите, а rate limiting е в паметта на процеса.
При няколко backend инстанции може да се добави Redis за споделени лимити.

## Временен AI — Groq

1. Създай акаунт и API ключ на https://console.groq.com/keys.
2. Използвай **Free plan** за тестване. Той има квоти и не е неограничен:
   https://console.groq.com/docs/rate-limits.
3. Добави следните настройки в `web-app/backend/.env`:

```dotenv
AI_PROVIDER=groq
GROQ_API_KEY=your_actual_key_here
GROQ_MODEL=qwen/qwen3.8-27b
```

4. Рестартирай `npm run dev` след промяна на ключа.

Ключът се използва само от Express. Никога не го добавяй в React, с префикс
`VITE_`, в git или в чат. `.env` е изключен чрез `.gitignore`.
API ключът е необходим — приложението не включва споделен публичен ключ.
Няма автоматично преминаване към платен модел или друг доставчик.
Без ключ чатът показва конкретна грешка, а не измислен „AI“ отговор.

Моделът отговаря на избрания език и получава скорошната история и текущия сценарий.
Express изчислява контекста със същата симулация, която използва интерфейсът.
При изрична команда може да променя сезон, час, облачност, вятър, слоеве и
избран град/централа. Всички предложени промени са ограничени до тези контроли.

Съобщенията, историята и сценарият се изпращат на Groq. Не изпращайте лични
данни или тайни при тестване. Историята се запазва според режима гост/профил,
описан по-горе. PostgreSQL не е необходим за самата AI интеграция.

Groq моделите и квотите могат да се променят. Моделът е конфигурируем чрез
`GROQ_MODEL`; проверете https://console.groq.com/docs/models.
Адаптерът очаква модел с JSON Object Mode. По подразбиране Qwen 3.8 работи
без допълнително reasoning за по-кратки тестови заявки.

## API и бъдещ MCP адаптер

`GET /api/health` показва конфигурирания доставчик и дали има ключ.
Това е проверка на конфигурацията, не доказателство за валиден ключ или активна
връзка с външния модел.

`POST /api/chat` приема:

```json
{
  "message": "Покажи зима вечер",
  "language": "bg",
  "history": [
    {"role": "user", "content": "Здравей"},
    {"role": "assistant", "content": "Здравей!"}
  ],
  "state": {
    "season": "autumn",
    "hour": 13,
    "cloud": 20,
    "wind": 45,
    "playing": false,
    "selected": "sofia",
    "layers": {"solar": true, "wind": true, "hydro": true, "demand": true, "flow": true}
  }
}
```

Успешен отговор:

```json
{
  "reply": "Показвам зима вечер.",
  "patch": {"season": "winter", "hour": 20},
  "provider": "groq",
  "model": "qwen/qwen3.8-27b"
}
```

Грешките са JSON с `code` и български `error`.
Лимитите връщат HTTP 429 и `Retry-After`. Има локален лимит
10 заявки/минута/IP, максимум 2 000 знака на въпрос, ограничена история и
25-секунден timeout към доставчика.

Когато AI екипът е готов:

- Добавете `backend/src/ai/mcp.js` с избрания MCP клиент, транспорт,
  автентикация и действителното име/схема на инструмента.
- Адаптерът предоставя `status()` и
  `generate({message,history,state,language}, {signal})`.
- Нормализирайте резултата до `{reply,patch,provider,model}` и го
  регистрирайте в `backend/src/ai/provider.js`.
- Тогава задайте `AI_PROVIDER=mcp`. Frontend и API договорът остават
  същите; валидирането на контролите остава в Express.

**MCP още не е реализиран или свързан.** Днес `AI_PROVIDER=mcp` връща ясна
грешка, вместо да симулира връзка. Необходимите endpoint, транспорт и tool
schema трябва да бъдат предоставени от другия екип.

`shared/energy.js` съдържа общия енергиен модел, а
`shared/chatContract.js` — входната валидация и позволените UI промени.
Layout-ът на картата, статистиките и чата не е променен.

За профили и история има също `GET /api/auth/session`,
`POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`,
`PUT /api/auth/preferences`, `GET /api/conversations`,
`GET /api/conversations/:id` и `PUT /api/conversations/:id`.
Мутациите изискват `X-Requested-With: energy-web-app`; React го изпраща
автоматично чрез same-origin Vite proxy. Токенът за сесия не се връща в JSON.

## Проверки и база данни

```sh
npm test
npm run build
```

AI тестовете използват mock HTTP отговори: не харчат квота и не изискват ключ.
Тестовете за профили използват in-memory repository, не реален PostgreSQL.
Включени са проверки за хеширане, сесии, достъп само до собствена история,
CSRF, езици, настройки и гост история. Те не заместват browser/live DB тест.
За live проверка добави своя ключ и изпрати въпрос през интерфейса.

API по подразбиране слуша само на 127.0.0.1. Не го публикувайте публично без
production защити и лимити: тестовият AI endpoint остава достъпен и за гости.
За различен frontend origin
настройте `CLIENT_ORIGIN`.
